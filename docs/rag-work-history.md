# RAG 작업 과정 정리 (R3, 2026-10-22 ~ 10-26)

R3가 RAG를 어떤 순서로, 왜 그렇게 만들었는지 되짚어 보는 문서입니다. 수치의 자세한 전후는 [optimization-log.md](optimization-log.md), 다른 역할에 보낸 요청은 [requests.md](requests.md), 남은 일은 [todo.md](todo.md)에 있습니다.

## 0. 출발점

- **해야 했던 일:** Agent(R2)가 쓰던 가짜 검색 `MockKnowledgeSearch`를 진짜 검색으로 바꾸기. 계약은 `search_knowledge(query, language, context) -> list[KnowledgeHit]` 하나.
- **지킨 원칙**
  - 요금·시간·위치 같은 사실은 **공식 출처를 직접 열어 확인한 것만** 문서에 쓴다. 확인 못 한 건 `<!-- TODO(R3) -->` 주석으로 숨긴다(사용자에게 안 보임).
  - 다른 역할의 레포는 고치지 않는다. 필요한 변경은 패치·이슈로 요청한다.
  - 레포는 공개 예정 → 비밀값·개인정보·얼굴 사진을 넣지 않는다.

## 4. 평가를 다루는 방식 (중요)

- 평가셋은 **실행 전에 고정**하고, 결과를 본 뒤에는 그 셋으로 "좋아졌다"고 말하지 않는다(회귀 확인용으로만).
- R6가 판정용으로 만든 셋(v3 등)은 **R6가 판정하기 전에는 R3가 돌리지 않는다.**
- 실패한 시도도 기록한다(PR #4 첫 버전). 왜 실패했는지가 다음 설계의 근거가 된다.

## 6. 다시 해 보는 법

```sh
uv run pytest -q                       # 테스트 (옆 레포가 있으면 계약 테스트까지)
uv run python eval/measure.py          # 평가셋 · 발췌 크기 · 메모리 · 검색 시간
set -a; . ../.env; set +a              # 아래 둘은 OpenAI 키 필요 (몇십 원)
uv run --project ../oneload-backend --with . python scripts/agent_live_check.py
uv run --project ../oneload-backend --with . python scripts/latency_check.py
```
