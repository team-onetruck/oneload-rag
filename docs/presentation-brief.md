# 발표 준비용: 한길 RAG 한눈에 보기

발표하는 분이 RAG 부분을 설명하고 질문에 답할 수 있게 정리했습니다. 숫자는 모두 직접 잰 값이고, 재는 방법과 전후 기록은 [optimization-log.md](optimization-log.md)에 있습니다. (작성: R3, 2026-10-26)

## 한 줄 요약

> 외국인 여행객의 질문에 **공식 출처로 확인한 안내 문서만 근거로** 답하게 하는 검색 모듈입니다. 모르는 건 지어내지 않고 "확인된 자료가 없다"고 답합니다.

## 1. 서비스 안에서의 위치

```text
사용자 (앱) → 백엔드 /messages → Agent (R2, LLM)
                                   ├─ 질문 이해 (LLM)
                                   ├─ RAG 검색 (R3) ← 안내 문서 14개
                                   ├─ 답변 작성 (LLM, 검색된 문서만 근거로, 출처 표시)
                                   └─ 답변 검증 (LLM, 문서에 답이 없으면 "확인된 자료 없음")
```

- 화면에는 답과 함께 **출처 링크와 확인 날짜**가 나옵니다.
- RAG는 Python 패키지(`hangil-rag`)로 백엔드 안에서 함수로 불립니다. 같은 기능을 MCP 서버(Docker)로도 열어 두었습니다.

## 2. 데이터: 안내 문서 14개

| 종류 | 문서 |
| --- | --- |
| 승차권 | 직통열차·일반열차 차이, 직통열차 표 사기(서울역), 일반열차 타는 법(1회용 교통카드) |
| 요금 | 직통열차 요금, 일반열차 역간 운임표, 교통 패스·카드 가격과 수수료 |
| 교통카드 | 1회용 교통카드 보증금 환급, 티머니 충전·환불, WOWPASS, 기후동행카드 단기권, 외국인용 교통카드 |
| 환승·이용 | 서울역 환승(1·4호선·KTX), 서울 지하철·버스 타는 법 |
| 도움 | 서울역 공항철도에서 도움받을 곳 (안내센터 → 1330 → 콜센터 순) |

- **모두 한국어·영어 두 언어.** 질문 언어에 맞춰 제목과 내용을 돌려줍니다.
- **공식 출처만:** 공항철도 홈페이지·여객운송약관·서울역 안내도, 서울시, 티머니, 한국관광공사 등. 문서마다 출처 URL과 확인 날짜가 붙어 있고, **14개 모두 담당자(R3)가 출처와 직접 대조**했습니다.
- **확인 못 한 사실은 숨김:** 공식 근거가 없는 내용(예: 직통열차 하차 후 전용 게이트)은 사용자에게 보이지 않는 메모로만 남기고, 전화 확인 뒤 넣습니다.
- **이용자 후기는 분리:** 블로그·포럼·영상에서 본 정보는 "미확인" 문서로 따로 두고, 서비스 검색에서는 뺍니다.
- **오래된 정보 경고:** 요금 문서는 90일, 나머지는 180일이 지나면 자동 테스트가 실패해 다시 확인하라고 알려 줍니다.

## 3. 검색 방법

| 단계 | 하는 일 |
| --- | --- |
| 범위 판정 | 문서에 없는 주제(호텔·날씨·항공권), 실시간 질문(빈 좌석·매진), 우리 문서가 값을 매기지 않은 가격(택시·KTX·리무진)은 **빈 결과** |
| 열차 필터 | 사용자가 직통/일반열차를 골랐으면 다른 열차 전용 문서는 뺌 |
| 점수 | 질문과 문서의 낱말 겹침 (한글은 2글자 조각이라 조사가 붙어도 맞음), 제목에 있으면 가중치 |
| 상위 3개 | Agent는 최대 3개 문서만 근거로 씀 |
| 발췌 | 문서 전체가 아니라 **질문과 맞는 소제목 하나만** LLM에 넘김 (표처럼 나누면 안 되는 문서는 통째로) |

**왜 벡터 검색(임베딩)이 아니라 키워드 검색인가:** 둘 다 만들어 같은 평가셋으로 비교했습니다. 문서 14개 규모에서는 키워드 검색이 정답을 더 많이 찾았습니다(42/43 vs 40/43). DB·API 비용도 없습니다. 문서가 많아지면 설정 하나(`RAG_BACKEND=pgvector`)로 바꿀 수 있게 만들어 두었습니다.

## 4. 성능 (직접 잰 값)

### A. RAG를 안 쓸 때 vs 쓸 때 (가장 중요)

같은 질문 56개를 **LLM(gpt-4o-mini)에 그대로** 물었을 때와 **우리 서비스(백엔드 + Agent + RAG)**에 물었을 때를 비교했습니다. LLM 채점관이 정답 문서와 대조해 채점했고, 틀렸다고 나온 답은 사람이 문서와 직접 대조해 확인했습니다. (2026-10-26, `scripts/compare_no_rag.py`)

| | RAG 없음 (LLM 단독) | RAG 사용 (우리 서비스) |
| --- | --- | --- |
| **정답이 문서에 있는 질문 24개** | 맞음 7 · **틀림 16** · 답 보류 1 | **맞음 22 · 틀림 0** · 답 보류 2 |
| **문서에 없는 질문 32개** (택시 요금, 호텔 가격, 여권 수수료 ...) | **금액·시간·규정을 단정 24** · 모른다고 함 8 | **모른다고 함 30** · 단정 2 (금액 없음) |

실제 답 예시:

| 질문 | RAG 없음 | RAG 사용 |
| --- | --- | --- |
| 직통열차 T1·T2 정상운임 비교 | "T1 약 9,500원, T2 약 10,000원" ❌ | "T1 18,500원, T2 19,100원" ✅ (공식 요금표) |
| 서울역 → 검암 일반열차 어른 운임 | "약 4,000원" ❌ | "2,050원 [1]" ✅ 출처 표시 |
| 택시 기본요금이 얼마예요? | "2023년 기준 약 3,800원" ❌ (실제 4,800원) | "확인된 자료가 없어서 추측하지 않을게요" |
| 직통열차 창가 좌석 변경 비용? | "추가 비용은 없습니다" (근거 없음) | "확인된 자료가 없어서 추측하지 않을게요" |

- **핵심 메시지:** LLM 혼자서는 그럴듯하지만 틀린 금액을 말합니다(정답 질문의 2/3를 틀림, 모르는 질문의 3/4에 금액을 단정). RAG를 쓰면 틀린 답이 0건이고, 모르는 질문 32개 중 30개는 모른다고 합니다.
- RAG 사용 쪽 "단정 2"는 금액이 아니라, 문서의 비슷한 내용을 끌어다 붙인 경우입니다("WOWPASS 재발급 수수료 없음", 티머니 단말기 오류 환불에 기후동행카드의 "3영업일"). "답 보류 2"는 문서에 답이 있는데 Agent가 보류한 경우입니다(경로 할인 조건, 엠패스 3일권). 둘 다 Agent 담당(R2)에게 전달했습니다.
- 질문: R6(QA)가 미리 고정한 48개 + 시나리오 16개 중 채점 가능한 56개. 실행 1회 결과입니다. 같은 질문도 실행마다 1~2개씩 결과가 달라질 수 있습니다.
- (10-26 정정) 처음 이 표는 측정 도구가 옛 RAG 빌드를 쓰고 있어서 RAG 쪽 숫자가 실제와 달랐습니다. 지금 버전으로 다시 잰 값입니다.

### B. 처음 버전 vs 지금 버전 (검색 단계)

처음 만든 버전(v0.1.0, 10-22)과 지금 버전(PR #4)을 같은 평가셋으로 쟀습니다. (`eval/measure.py`)

| 평가셋 (정답 상위 3개 · 범위 밖 질문 차단) | 처음 v0.1.0 | 지금 |
| --- | --- | --- |
| R3 47문항 | 39/43 · 3/4 | 42/43 · 4/4 |
| R3 보류 검증 28 | 16/16 · 5/12 | 16/16 · 7/12 |
| R6 32문항 | 19/20 · 3/12 | 20/20 · 10/12 |
| R6 v2 40 | 20/20 · 5/20 | 20/20 · 20/20 |
| R6 v3 48 | 21/24 · 4/24 | 24/24 · 8/24 |
| R6 v4 48 | 24/24 · 6/24 | 24/24 · 8/24 |
| **합계** | **정답 139/147 · 차단 26/96** | **정답 146/147 · 차단 57/96** |
| LLM에 넘기는 글 (질문당 중앙값) | 3,398자 | **2,078자** |

- 바뀐 것: 문서 13 → 14개(서울역 환승), 범위 밖·실시간 질문 거르기, 가격 질문 판정, 발췌 줄이기
- 발췌는 한때 1,536자까지 줄였지만, 소제목만 떼어 주면 답이 빠지는 경우가 있어(일반열차 전체 운임표, 어느 패스 가격인지) 소제목 줄을 붙이고 운임표 문서는 통째로 넘기도록 되돌렸습니다. 정확도를 우선했습니다.
- 처음 버전의 R3 47문항에는 그 뒤에 추가한 문서(서울역 환승)를 묻는 질문 3개가 포함돼 있어 처음 버전에 조금 불리합니다.

정답이 상위 3개 안에 드는 비율 / 범위 밖 질문에 빈 결과를 낸 비율입니다. 질문은 R3·R6(QA)가 만든 합성 질문입니다.

| 평가셋 | 서비스 버전 (v0.3.0) | 개선 버전 (PR #4, 판정 대기) |
| --- | --- | --- |
| R3 47문항 | 42/43 · 4/4 | 42/43 · 4/4 |
| R6 32문항 | 20/20 · 11/12 | 20/20 · 10/12 |
| R6 v2 40문항 | 17/20 · 15/20 | 20/20 · 20/20 |
| R6 v3 48문항 | 21/24 · 14/24 | 24/24 · 8/24 |
| R6 v4 48문항 | 16/24 · 18/24 | **24/24** · 8/24 |

- QA(R6)와 합의한 기준: **검색은 정답을 놓치지 않기(상위 3개 ≥ 90%)**, 범위 밖 질문은 **최종 답변에서 근거 없는 말을 하지 않기**로 잽니다. 검색 단계의 범위 밖 차단은 참고 지표입니다.
- v2·v3·v4는 R6가 한 번 판정한 뒤 공개된 셋이라 참고용입니다. **개선 버전의 공식 판정은 R6의 새 평가셋으로 받을 예정**입니다.

## 5. 발표에서 쓸 만한 문장

- "LLM에 그대로 물으면 직통열차 요금을 9,500원이라고 틀리게 말합니다. RAG를 붙이면 공식 요금표대로 18,500원이라고 답하고 출처를 보여 줍니다. 같은 질문 24개에서 틀린 답이 16개에서 0개가 됐습니다."
- "답변의 근거는 공식 출처로 확인한 문서 14개뿐이고, 모든 답에 출처와 확인 날짜를 붙입니다."
- "문서에 없는 질문(택시 요금, 호텔 가격 등)에는 금액을 지어내지 않습니다. QA가 만든 48개 질문(v4)을 실제 LLM으로 돌려 범위 밖 24개에서 지어낸 정보가 0건이었습니다."
- "검색은 0.3ms라 응답 시간에 거의 영향이 없고, LLM에 넘기는 글은 관련 부분만 골라 약 60%로 줄였습니다."
- "벡터 검색도 구현해 비교했지만, 지금 규모에서는 키워드 검색이 더 정확해서 그쪽을 택했습니다."

## 6. 정직하게 말해야 할 한계

- **평가 질문은 합성 질문입니다.** 실제 사용자 질문 로그는 아직 없습니다.
- **개선 버전(PR #4)은 아직 서비스에 들어가지 않았습니다.** QA 판정 뒤 반영 예정입니다(위 표의 "서비스 버전"이 지금 서비스).
- **전화로만 확인할 수 있는 사실이 남아 있습니다.** 예: 직통열차에서 내려 지하철로 갈아타는 전용 게이트, 보증금 환급기 정확한 위치, 안내센터 운영 시간. 지금은 서비스가 이 내용을 말하지 않습니다.
- **사진 위치 인식 정확도는 미측정입니다.** 현장 사진 정답이 없습니다(RAG가 아니라 사진 인식 쪽 한계).
- 키워드 검색이라 같은 뜻의 다른 말("표"와 "승차권")을 놓칠 때가 있습니다.

## 7. 예상 질문과 답

| 질문 | 답 |
| --- | --- |
| 왜 LLM에 바로 묻지 않고 RAG를 쓰나요? | 직접 비교했습니다. LLM 단독은 정답이 있는 질문 24개 중 16개를 틀렸고(요금을 틀린 금액으로), 모르는 질문 32개 중 24개에 금액을 단정했습니다. RAG를 쓰면 틀린 답 0건, 모르는 질문 32개 중 30개는 모른다고 합니다(4-A). |
| 문서 내용이 바뀌면? | 문서(Markdown)만 고치면 됩니다. 확인 날짜가 오래되면 테스트가 알려 줍니다. 고친 뒤 태그를 새로 달면 백엔드가 받아 갑니다. |
| 벡터 DB는 안 쓰나요? | pgvector로 구현해 비교했습니다. 지금 규모(문서 14개)에서는 키워드 검색이 더 정확해 기본값으로 쓰고, 설정 하나로 바꿀 수 있습니다. |
| 모르는 질문은 어떻게 처리하나요? | 검색 단계에서 범위 밖·실시간 질문을 거르고, Agent가 문서에 답이 없으면 "확인된 자료가 없다"고 답합니다. 금액을 지어낸 답은 0건이었고, 문서의 비슷한 내용을 끌어다 쓰는 경우가 드물게 있어 Agent 검증을 개선하고 있습니다. |
| 문서 전체를 LLM에 넣나요? | 아니요. 문서를 소제목 단위로 나눠 두고, 질문과 맞는 부분만 넘깁니다(전송량 약 60%). |
| 응답이 느리면? | 검색은 0.3ms로 영향이 없습니다. 시간 대부분은 LLM 호출(이해·답변·검증)입니다. |
| 정확도는 어떻게 쟀나요? | 질문을 실행 전에 고정한 평가셋으로 잽니다. QA(R6)가 따로 만든 평가셋으로도 판정받습니다. |
