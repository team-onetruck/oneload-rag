# 발표 준비용: 한길 RAG 한눈에 보기

발표하는 분이 RAG 부분을 설명하고 질문에 답할 수 있게 정리했습니다. 숫자는 모두 직접 잰 값이고, 재는 방법과 전후 기록은 [optimization-log.md](optimization-log.md)에 있습니다. (작성: R3, 2026-10-26)

## 한 줄 요약

> 외국인 여행객의 질문에 **공식 출처로 확인한 안내 문서만 근거로** 답하게 하는 검색 모듈입니다. 모르는 건 지어내지 않고 "확인된 자료가 없다"고 답합니다.

## 1. 서비스 안에서의 위치

```
사용자 (앱) → 백엔드 /messages → Agent (R2, LLM)
                                   ├─ 질문 이해 (LLM)
                                   ├─ RAG 검색 (R3) ← 안내 문서 14개
                                   ├─ 답변 작성 (LLM, 검색된 문서만 근거로, 출처 표시)
                                   └─ 답변 검증 (LLM, 문서에 답이 없으면 "확인된 자료 없음")
```

- 화면에는 답과 함께 **출처 링크와 확인 날짜**가 나옵니다.
- RAG는 Python 패키지(`hangil-rag`)로 백엔드 안에서 함수로 불립니다. 같은 기능을 MCP 서버(Docker)로도 열어 두었습니다.

## 2. 데이터: 안내 문서 14개

| 종류 | 문서 |
| --- | --- |
| 승차권 | 직통열차·일반열차 차이, 직통열차 표 사기(서울역), 일반열차 타는 법(1회용 교통카드) |
| 요금 | 직통열차 요금, 일반열차 역간 운임표, 교통 패스·카드 가격과 수수료 |
| 교통카드 | 1회용 교통카드 보증금 환급, 티머니 충전·환불, WOWPASS, 기후동행카드 단기권, 외국인용 교통카드 |
| 환승·이용 | 서울역 환승(1·4호선·KTX), 서울 지하철·버스 타는 법 |
| 도움 | 서울역 공항철도에서 도움받을 곳 (안내센터 → 1330 → 콜센터 순) |

- **모두 한국어·영어 두 언어.** 질문 언어에 맞춰 제목과 내용을 돌려줍니다.
- **공식 출처만:** 공항철도 홈페이지·여객운송약관·서울역 안내도, 서울시, 티머니, 한국관광공사 등. 문서마다 출처 URL과 확인 날짜가 붙어 있고, **14개 모두 담당자(R3)가 출처와 직접 대조**했습니다.
- **확인 못 한 사실은 숨김:** 공식 근거가 없는 내용(예: 직통열차 하차 후 전용 게이트)은 사용자에게 보이지 않는 메모로만 남기고, 전화 확인 뒤 넣습니다.
- **이용자 후기는 분리:** 블로그·포럼·영상에서 본 정보는 "미확인" 문서로 따로 두고, 서비스 검색에서는 뺍니다.
- **오래된 정보 경고:** 요금 문서는 90일, 나머지는 180일이 지나면 자동 테스트가 실패해 다시 확인하라고 알려 줍니다.

## 3. 검색 방법

| 단계 | 하는 일 |
| --- | --- |
| 범위 판정 | 문서에 없는 주제(호텔·날씨·항공권), 실시간 질문(빈 좌석·매진), 우리 문서가 값을 매기지 않은 가격(택시·KTX·리무진)은 **빈 결과** |
| 열차 필터 | 사용자가 직통/일반열차를 골랐으면 다른 열차 전용 문서는 뺌 |
| 점수 | 질문과 문서의 낱말 겹침 (한글은 2글자 조각이라 조사가 붙어도 맞음), 제목에 있으면 가중치 |
| 상위 3개 | Agent는 최대 3개 문서만 근거로 씀 |
| 발췌 | 문서 전체가 아니라 **질문과 맞는 소제목 하나만** LLM에 넘김 |

**왜 벡터 검색(임베딩)이 아니라 키워드 검색인가:** 둘 다 만들어 같은 평가셋으로 비교했습니다. 문서 14개 규모에서는 키워드 검색이 정답을 더 많이 찾았습니다(42/43 vs 40/43). DB·API 비용도 없습니다. 문서가 많아지면 설정 하나(`RAG_BACKEND=pgvector`)로 바꿀 수 있게 만들어 두었습니다.

## 4. 성능 (직접 잰 값)

### 검색 품질

정답이 상위 3개 안에 드는 비율 / 범위 밖 질문에 빈 결과를 낸 비율입니다. 질문은 R3·R6(QA)가 만든 합성 질문입니다.

| 평가셋 | 서비스 버전 (v0.3.0) | 개선 버전 (PR #4, 판정 대기) |
| --- | --- | --- |
| R3 47문항 | 42/43 · 4/4 | 42/43 · 4/4 |
| R6 32문항 | 20/20 · 11/12 | 20/20 · 12/12 |
| R6 v2 40문항 | 17/20 · 15/20 | 19/20 · 20/20 |
| R6 v3 48문항 | 21/24 · 14/24 | 22/24 · 8/24 |

- v2·v3는 R6가 한 번 판정한 뒤 공개된 셋이라 참고용입니다. **개선 버전의 공식 판정은 R6의 새 평가셋으로 받을 예정**입니다.
- 개선 버전은 검색 단계에서 범위 밖을 덜 거르는 대신 정답을 놓치지 않는 쪽입니다. 대신 "답할지"는 Agent가 판단합니다. 아래 답변 단계 결과가 그 근거입니다.

### 답변 단계 (실제 LLM gpt-4o-mini, R6 v3 48문항)

| | 결과 |
| --- | --- |
| 범위 밖 질문 24개 | **지어낸 금액·정보 0건** (21개 바로 거절, 3개는 "자료에 그 정보가 없다"고 답함) |
| 정답 질문 24개 | 20개 답변 (출처 표시) |

### 속도·자원

| 항목 | 값 |
| --- | --- |
| RAG 검색 1회 | **약 0.2~0.3ms** |
| 메시지 하나 전체 응답 | 약 2.8초 (중앙값). **이 중 98~99%가 LLM 호출**, RAG 검색은 0% |
| LLM에 넘기는 문서 양 | 질문당 중앙값 3,398자 → **1,618자 (49%)** (관련 소제목만 넘기도록 개선) |
| 검색기 메모리 | 약 1.4MB |
| 자동 테스트 | 128개, GitHub CI에서 다른 레포(Agent·백엔드·지도)와의 연결까지 매번 확인 |

## 5. 발표에서 쓸 만한 문장

- "답변의 근거는 공식 출처로 확인한 문서 14개뿐이고, 모든 답에 출처와 확인 날짜를 붙입니다."
- "문서에 없는 질문(택시 요금, 호텔 가격 등)에는 금액을 지어내지 않습니다. 실제 LLM으로 48개 질문을 돌려 범위 밖 24개에서 지어낸 정보가 0건이었습니다."
- "검색은 0.3ms라 응답 시간에 거의 영향이 없고, LLM에 넘기는 글은 관련 부분만 골라 절반으로 줄였습니다."
- "벡터 검색도 구현해 비교했지만, 지금 규모에서는 키워드 검색이 더 정확해서 그쪽을 택했습니다."

## 6. 정직하게 말해야 할 한계

- **평가 질문은 합성 질문입니다.** 실제 사용자 질문 로그는 아직 없습니다.
- **개선 버전(PR #4)은 아직 서비스에 들어가지 않았습니다.** QA 판정 뒤 반영 예정입니다(위 표의 "서비스 버전"이 지금 서비스).
- **전화로만 확인할 수 있는 사실이 남아 있습니다.** 예: 직통열차에서 내려 지하철로 갈아타는 전용 게이트, 보증금 환급기 정확한 위치, 안내센터 운영 시간. 지금은 서비스가 이 내용을 말하지 않습니다.
- **사진 위치 인식 정확도는 미측정입니다.** 현장 사진 정답이 없습니다(RAG가 아니라 사진 인식 쪽 한계).
- 키워드 검색이라 같은 뜻의 다른 말("표"와 "승차권")을 놓칠 때가 있습니다.

## 7. 예상 질문과 답

| 질문 | 답 |
| --- | --- |
| 왜 LLM에 바로 묻지 않고 RAG를 쓰나요? | 요금·위치 같은 사실을 LLM이 지어낼 수 있어서입니다. 확인된 문서만 근거로 쓰고 출처를 보여 줍니다. |
| 문서 내용이 바뀌면? | 문서(Markdown)만 고치면 됩니다. 확인 날짜가 오래되면 테스트가 알려 줍니다. 고친 뒤 태그를 새로 달면 백엔드가 받아 갑니다. |
| 벡터 DB는 안 쓰나요? | pgvector로 구현해 비교했습니다. 지금 규모(문서 14개)에서는 키워드 검색이 더 정확해 기본값으로 쓰고, 설정 하나로 바꿀 수 있습니다. |
| 모르는 질문은 어떻게 처리하나요? | 검색 단계에서 범위 밖·실시간 질문을 거르고, Agent가 문서에 답이 없으면 "확인된 자료가 없다"고 답합니다. 실제 확인에서 지어낸 정보 0건이었습니다. |
| 문서 전체를 LLM에 넣나요? | 아니요. 문서를 소제목 단위로 나눠 두고, 질문과 맞는 부분만 넘깁니다(전송량 49%). |
| 응답이 느리면? | 검색은 0.3ms로 영향이 없습니다. 시간 대부분은 LLM 호출(이해·답변·검증)입니다. |
| 정확도는 어떻게 쟀나요? | 질문을 실행 전에 고정한 평가셋으로 잽니다. QA(R6)가 따로 만든 평가셋으로도 판정받습니다. |
